R4OS UPDATE PACKAGES IN STUDIO

Use the assigned VM and declared project update tools. Package, component and
target OS release versions identify different things. Read the actual project
pins and native source binding before relying on an API or update requirement.

1. Select the package inputs

Read studio_read_update_package with action=options. Use the current
configurationRevision and confirmed project build artifact IDs. Supply the
explicit package, component and target release metadata and requirements to
studio_plan_update_package. Use the SDK catalogue target from the artifact.
Choose a target supported by the actual VM and the project's source manifest.

The plan binds the artifact and manifest bytes, target and requirements, and
the selected qualified R4UPack profile. Review the plan and retain its ID and
SHA-256. Use System → Updates → Tools → R4UPack to inspect or select the
packer profile when required. Preserve the selected project SDK, Contract and
compiler.

2. Build the package

Call studio_build_update_package with planId and planSha256. The tool waits for
its original packaging job. Inspect the real packer exit and the immutable
package artifact ID, size and SHA-256. A successful build establishes the
package artifact and its bound inputs. Guest compatibility is checked on the
assigned VM.

3. Check the VM and transfer the package

Use the separately permitted VM-start action when startup is part of the task.
Call studio_check_update_vm with packageArtifactId for the assigned VM's
current VER, SYSUPD STATUS, installed release and inventory. Resolve unavailable
development access, unsupported target or conflicting native state before upload.

Call studio_upload_update_package with the same packageArtifactId. The tool
transfers the package to its reserved Inbox temporary path, confirms SFTP
CLOSE, verifies the complete size and SHA-256 by readback, and publishes by
create-only rename. Retain the resulting transfer job ID and package identity.
Use the tool's result to verify successful transfer.

4. Stage the selected packages

Call studio_install_update_package with 1–16 exact own transferJobIds for the
same target release. Studio runs native VERIFY against the current inventory,
then STAGE. STAGE can apply a live persistent update. Inspect the original
native outcome and installed-state evidence. A prepared batch has status
awaiting commit.

Commit only with the user authorization for the specific VM, update and
reboot, and the session's Commit permission. Read the current update record
and pass updateId, updateRevision, vmRevision, targetRelease, batchId and
confirmReboot=true to studio_commit_update. Studio submits the original COMMIT
once and reads bounded post-boot evidence on the bound VM.

5. Verify and recover the original operation

Use studio_read_update_package to read the original jobs and update records.
Use studio_verify_update with the current updateId and updateRevision for
native terminal state, installed component inventory and full artifact hashes.
Bind the evidence to the recorded VM, batch, transaction, components and
packages. Report transfer, awaiting commit, confirmed installation, rollback
and incomplete proof according to the observed state.

If a response is lost, inspect the original operation and its current
receipts before any further effect. The tool waits on the original job while
the call is active. A newly requested read can verify the same operation.

Use studio_resume_update for an explicitly requested, freshly verified owned
transaction or batch. A prepared batch resume can commit and reboot and
requires the corresponding authorization, Commit permission and
confirmReboot=true. A rolled_back journal with a rolling-back batch requires
a separately authorized batch resume for native finalization. Use
studio_abort_update for a verified owned prepared batch before a durable
batch transaction. Use studio_rollback_update for the exact latest proved own
update when rollback and possible reboot are authorized and the Rollback
permission is enabled.

After correlated terminal proof or confirmed abort, use
studio_cleanup_update_transport for this update's original matching Inbox
files. Preserve partial, different or foreign files and the original
diagnostic evidence. Studio's VM reservation coordinates its own workers.
Check native ownership and state before any write if another update client
may be active.
